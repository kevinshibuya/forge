# The output contract is engine-enforced, and a run can decline inside it

Every structured run used to end with one prompt line, "respond with JSON only", and a parse of whatever came back. Run 111 answered a placeholder idea with prose explaining why it would not write the post, and was recorded as `invalid_output`. Run 113 did the same with a fenced JSON object that carried the wrong keys. Both were the model behaving well and the harness failing to tell that apart from a broken run. The contract was a sentence in the prompt, and a sentence is not a mechanism.

The CLI enforces a shape through `--json-schema`. Probed on 2.1.260 and again on 2.1.261 (`app/api/scripts/probe-output-contract.mjs`): the flag is a tool input schema, so a `oneOf` at the top level is refused with `input_schema does not support oneOf, allOf, or anyOf at the top level`, and the union has to sit under a required property. The parsed object arrives as `structured_output` on the `subtype: success` result line, while `result` stays a string. The CLI fulfils the schema through a tool call named `StructuredOutput`, which the research fence (`--tools Read,WebSearch,WebFetch`) does not filter out. The real `DraftOutputSchema` and `TriageOutputSchema`, with `minLength`, `integer` and nullable `anyOf`, are accepted unchanged. And the finding that shaped the runner: told to ignore the schema, the model answered in prose and the CLI returned a success line with no `structured_output` and no error. Enforcement is not absolute, so the runner cannot trust a success line on its own.

Decision. One shared module (`app/shared/src/contract.ts`) turns a kind's zod schema into the enforced JSON Schema: `{ result: <payload> | <decline> }`, nothing else. The decline envelope is `{ outcome: 'declined', reason, question? }`. The runner is the single seam: it passes the schema for every schema-bearing kind, requires `structured` back when it asked for one (none is `invalid_output`, with no fallback to parsing the prose), unwraps the wrapper (bare is malformed), and either parses the payload with the kind's zod schema or records a decline. A decline is `status: failed`, failure kind `declined`, the envelope kept in a `declined` column, its reason as the error, its tells linted, its usage recorded, no revision written, `parsedOk: true` because the contract was honoured. On success the stored output is the bare payload, so every existing reader of `run.output` keeps parsing what it always parsed. The constitution's closing line now says where the prompt's shape example goes (the `result` value) and how to decline; the prompts' own shape examples stay as documentation. No repair pass, no retry. The codex engine refuses a schema-bearing request outright, since no codex kind carries a schema and its `--output-schema` is not wired.

## Considered options

- **A repair pass.** A second call that asks the model to fix its output. Rejected: it spends a call to paper over a broken contract and hides the bug that broke it.
- **Retry once.** Rejected for the same reason, with the added cost of a timeout doubling.
- **A variant schema per kind.** One decline shape per payload. Rejected: the envelope is the same everywhere, and one module owns it.
- **A fourth run status, `declined`.** Rejected: every reader of `status` would need a new branch, and a decline is a failure to produce the payload. It is a failure kind, next to the others.
- **`succeeded` with a declined payload.** Rejected: the launchers write the post body on `ok`, and a decline must never reach that branch.
- **Text fallback when `structured` is missing.** Parse the prose the old way. Rejected by both review legs: it would let the exact case that motivated this ADR back in through the side door.
- **Codex `--output-schema` now.** Rejected: no codex kind carries a schema, `ProcessEngine.run` has no cleanup hook for a temp schema file, and dead lifecycle code is worse than an explicit refusal.

## Consequences

- Every schema-bearing kind (`draft`, `refine_selection`, `triage`, `retro`, `image_review`, `image_variate`, the managed `image_plan` step) is enforced at one seam. A future kind gets the contract by passing its schema to `execute` or to `executeManaged`'s `call`.
- A prompt's shape example is documentation of the payload under `result`, not the mechanism.
- `invalid_output` now means one of four things: no structured result, the CLI's `error_max_structured_output_retries`, a wrapper without `result`, or a zod-only refinement the JSON Schema cannot carry (`RetroProposalSchema.superRefine`, a `.trim()`). Each is a schema-design or harness bug to file, never a CLI regression to wait out.
- The `StructuredOutput` tool call is not a research tool: it is excluded from the 15-call cap and from the tool-call audit, or a research run would die at the moment it answered.
- A decline is visible where the operator is: the failure card names it in the ink tone with the question set apart, and the workspace's failure strip carries the same until a newer draft succeeds.

## Amended for v2 (2026-09-24)

The contract holds on the `api` backend (ADR 0019) with the same envelope: `{ result: <payload> | <decline> }` as an `anyOf` under a required property with a `const` tag per branch, which is the shape both providers accept (`docs/research/2026-09-24-r13-api-backend.md`); a `oneOf` at the top level is refused by them as it was by the CLI. Two things the CLI enforced the API cannot: `minLength`, `maxLength`, `minimum`, `maximum` and `minItems` above 1 are stripped by the SDK before the call. So a Form's length and structure rules leave the schema and become a deterministic check after the run that feeds the Draft score's fit part and offers a shorten refine; an overrun is a low score, never `invalid_output`, and this ADR's meaning of `invalid_output` (a broken contract is a bug) survives exactly because the constraints the model cannot be held to are no longer in the contract. A provider-level refusal (OpenAI's `refusal` item, Anthropic's refusal stop reason) is a second path to `declined`, beside the in-schema decline. No repair pass and no retry, as before; the one retry the `api` engine makes is for transport and rate-limit errors, recorded on the Run, never for the model's output.
